# Architecture

## Overview

Badger is a local-first desktop application built as a Tauri shell around a SvelteKit single-page app. The frontend renders the user interface and calls Rust commands through Tauri's `invoke()` bridge. The Rust backend owns persistence, validation, reporting queries, backup/restore logic, and file-system access.

## Main parts

### Frontend

- Located under `src/`
- Uses SvelteKit in SPA mode with `ssr = false`
- Uses Tauri's WebView runtime instead of a server-rendered deployment model
- Calls backend commands with `@tauri-apps/api/core`

The main user-facing areas are:

- `/` — Today: one Tasks card (overdue, due today, or with a sent reminder), today's logged time, and a Mon–Sun week strip with progress against the daily hours target
- `/timesheet` — timesheet entry and editing; date filter includes Single Day, and `?day=YYYY-MM-DD` opens it on that day (an invalid `day` is ignored)
- `/tasks` — tasks grouped Overdue / Today / Tomorrow / This week / Later / No date under a session-only scope filter (All / Today / Tomorrow / This week), plus a folded Completed group (All only; this week, "Show older" for the rest), with quick-add on top and a details side panel that exists only while a task is selected; `?id=<id>` selects a task and `?new=1` focuses quick-add; see Tasks
- `/reports/weekly` — ISO-week report view
- `/reports/monthly` — month report view with expandable grouping, the month's travel, and a copy-month text export
- `/notes` — a folder tree of notes on the left (notes first, pinned first, then folders, each group in manual order; see Notes folders) that becomes a flat list of ranked hits with highlighted title, snippet and folder path while searching via the `search_notes` command, and a markdown live-preview editor on the right; the selected note lives in the URL (`?id=12`)
- `/playground` — saved JavaScript scripts: a script list on the left (title filter, ⌘N), an editor above a console on the right, Run (⌘↵) and Stop; see Playground
- `/travel` — month-scoped list of business trips (date, from/to, optional km and kr) with inline add, edit, repeat, and delete
- `/settings` — customer and project management (cards with inline add, rename, default, and delete), preferences (System/Light/Dark appearance), backup/restore, and dev-only seed tooling

### Backend

- Located under `src-tauri/src/`
- Starts from `main.rs` and delegates to `badger_lib::run()`
- Registers Tauri commands in `lib.rs`
- Stores a shared SQLite pool and logging guard in Tauri managed state

The backend is organized around command modules:

- `customers` and `projects` for reference data (names are trimmed and unique case-insensitively: customers globally, projects per customer)
- `issues` and `time_entries` for core timesheet operations
- `tasks` for tasks and their reminders (`list_tasks`, `create_task`, `update_task`, `complete_task`, `undo_complete_task`, `reopen_task`, `delete_task`, `create_issue_for_task`, and `add_`/`update_`/`delete_`/`snooze_`/`dismiss_task_reminder`); `task_scheduler` (a top-level module, not a command module) fires reminders and `recurrence` (also top-level) holds the repeat rules; see Tasks
- `travel` for business trips, listed per month
- `apple_sync` for Apple Reminders sync (`get_apple_sync_status`, `set_apple_sync_enabled`, `request_apple_sync_access`, `sync_apple_reminders_now`, `recreate_apple_sync_lists`, `apple_sync_delete_anyway`); the engine is the top-level `apple_sync/` module (not a command module); see Apple Reminders sync
- `folders` for note folders (`list_folders`, `create_folder`, `rename_folder`, `move_folder`, `delete_folder`) and `move_note`; see Notes folders
- `notes` for markdown and JSON notes (create, rename, body save, `set_note_kind`, pin, delete), the list excerpt, which is computed in Rust, full-text search (`search_notes`, `search_index_stats`, `rebuild_search_index`), and links (`create_note_titled`, `list_tag_suggestions`, `get_link_targets`, `list_backlinks`)
- `semantic` for semantic note search: the lifecycle commands (`get_semantic_status`, `enable_semantic_search`, `cancel_semantic_download`, `remove_semantic_model`, `rebuild_semantic_index`) live in `commands/semantic.rs`; the engine is the top-level `semantic/` module (not a command module); see Semantic search
- `scratchpad` for the scratchpad (`get_scratchpad`, `set_scratchpad_body`, `save_scratchpad_as_note`); see Scratchpad
- `handovers` for handovers (`get_handover`, `list_handovers`, `save_handover`, `dismiss_handover`, `save_handover_as_note`); see Handovers
- `scripts` for saved playground scripts (`create_script`, `list_scripts`, `get_script`, `update_script_title`, `update_script_body`, `delete_script`) and `playground` for running them (`run_script`, `stop_script`, `script_running`); the engine is the top-level `js_runner/` module (not a command module); see Playground
- `markdown` for `render_markdown`, which turns note markdown into safe HTML (read view, copy as HTML)
- `note_links` (a top-level module, not a command module) for the `#tag` / `[[wikilink]]` extractor and entity slugs; see Notes links
- `reports` for weekly and monthly rollups
- `backup` for gzipped JSON export and import (restore also reads plain `.json`)
- `settings` for app preferences (theme, daily hours target, command palette shortcut and last-used project/issue, expanded note folders) stored in `app_settings`
- `startup_backup` for automatic daily backups (folder, flat file names, retention, `BackupState` lock and status) and `backup_crypto` for their optional `age` encryption
- `flush_guard` for the quit/close guard (see Notes editor)
- `updater` for in-app updates (`check_for_update`, `install_update`); see Updater
- `dev_seed` for debug-only sample data

## Data flow

The core request path is:

```text
Svelte component
  -> invoke("command_name", payload)
  -> Tauri command in Rust
  -> sqlx query against SQLite
  -> serialized result back to the frontend
```

### Theme

Dark mode uses Tailwind's `darkMode: "class"`: a `dark` class on `<html>` activates the `dark:` variants in `app.css` and markup. Dark surfaces use Tailwind's `neutral` grays; light mode uses `slate`. The theme mode (`system`, `light`, `dark`) is stored in `app_settings` via `get_theme`/`set_theme`; `src/lib/theme-state.svelte.ts` applies it (class, CSS `color-scheme`, native window theme) and mirrors it to `localStorage` so the inline script in `src/app.html` paints the right theme before the app loads. The setting is not part of backups.

### Command palette

`src/lib/components/CommandPalette.svelte` is mounted in the root layout and listens for its shortcut on `window` in the capture phase, so it opens over text fields and modals and Esc closes only the palette. The shortcut (default `Meta+K`, configurable in Settings › Preferences) and the last project/issue used for Log time live in `app_settings` (`get_palette_settings`, `set_palette_shortcut`, `set_palette_last_used`) and are not part of backups. Shortcut rules (needs ⌘/⌃/⌥, macOS-reserved combos refused), filtering and hours/date parsing are pure helpers in `src/lib/palette.ts`. After logging time the palette bumps a counter in `src/lib/palette-state.svelte.ts` (`changes.timeEntries`); the Timesheet and Today pages reload when it changes. "New task" (aliases: New todo, `remind …`, `påminn …`) goes through the same quick-add mapping as `/tasks` (see Tasks) and the shared tasks state, so no counter is needed. The same module drives the layout's `Toast`. Pages can open the Log time flow with `requestLogTime(prefill?)` in the same module: the palette consumes the request, and a prefill with a project and issue (Today's task [Log] button) jumps straight to the hours step. If the prefill's project no longer exists, the normal project step is shown.

### Menu bar and global shortcut

`src-tauri/src/tray.rs` adds a menu-bar item (the app icon, no title) with a native menu: "Today: X of Y h logged", up to five tasks needing attention (overdue, due today or with a sent reminder, like Today's Tasks card; "Overdue ·" or the due time as prefix) plus "N more…", then New Task…, Log Time…, Open Badger and Quit Badger. A task item opens it like a notification click (`task_scheduler::open_tasks`); "Quit Badger" calls `app.exit`, so the flush guard runs. Rust shows the window and emits `app-action` (`new-task` → `/tasks?new=1`, `log-time` → the palette's Log time flow), which the root layout handles. `tray::nudge()` asks a background loop to rebuild the menu: on every scheduler tick (date rollover), in `tasks_refreshed`, and after time entry writes; an unchanged model is not rebuilt, so an open menu stays put.

`src-tauri/src/global_shortcut.rs` registers one system-wide shortcut through `tauri-plugin-global-shortcut` (Rust-only). It is off until set in Settings › Preferences › Global shortcut (same recorder and rules as the palette shortcut), stored as `global_shortcut` in `app_settings` in the palette's format (`Meta` becomes the plugin's `Super`), registered at launch, and not part of backups. Pressing it opens the floating palette (`src-tauri/src/palette_window.rs`) instead of bringing up the main window: a frameless, transparent, always-on-top `palette` window on the monitor under the cursor, built hidden whenever a shortcut is registered (a press then only shows it: creating a window can activate Badger) and hidden again after use, loading `/palette` (the root layout renders only that page there, without nav, toasts or app wiring). It runs `CommandPalette.svelte` with `floating`: always open, no backdrop, the window sized to the card. Log time and New task finish inside it (a short confirmation, then it hides; logging emits `palette://time-entries-changed` so the main window bumps `changes`); Go to, notes, New note/script, Scratchpad and Write handover call `palette_to_main`, which hides it, shows the main window and re-emits the action as `app-action` (`goto` with `href`, `scratchpad`, `handover`). On macOS it is a non-activating `NSPanel` (`tauri-nspanel`, plugin registered in `lib.rs`), like Spotlight: it takes the keyboard without activating Badger, so the menu bar stays on the app in front and focus returns there when it hides. The panel replaces Tauri's window delegate, so its resign-key and should-close callbacks stand in for Tauri's focus and close events, and all panel calls run on the main thread. Esc, pressing the shortcut again or clicking another app hides it. ⌘W only hides it, and the flush guard ignores it. Transparency needs `tauri`'s `macos-private-api` feature (`macOSPrivateApi` in `tauri.conf.json`); its permissions are in `capabilities/palette.json`. `set_global_shortcut` registers before storing, so a combination another app owns is refused ("That shortcut is already used by another app") and the previous one stays.

### Today

Today (`src/routes/+page.svelte`) aggregates in the frontend: it loads the current week's `list_time_entries` and the daily target, and the pure totals helpers live in `src/lib/today.ts` (tested in `tests/today.test.mjs`). There are no dedicated list/report commands. The one Tasks card reads the shared list (see Tasks) and shows open tasks that are overdue, due today, or have a sent reminder (`todayTasks` in `src/lib/tasks.ts`), with the same row and completion check as `/tasks`; issue-linked rows keep a Log time button. The week runs Monday–Sunday and the weekly target is 5 × the daily target. The daily target is stored in `app_settings` via `get_daily_target`/`set_daily_target` (default 8, range 0–24, 0 turns the progress UI off, an invalid stored value falls back to 8), edited in Settings › Preferences, and is not part of backups. The page reloads when the palette bumps `changes`.

### Notes editor

The editor is CodeMirror 6 (`@codemirror/*` packages only: no `codemirror` meta-package or basicSetup), hosted by `src/lib/components/NoteEditor.svelte`. The live preview is written in this repo under `src/lib/editor/` rather than taken from a library, because the existing ones are alpha or stale. It hides markdown markers except on the lines touched by the selection and renders GFM tables as a block widget (raw source shows while the cursor is inside the table). Markdown links are styled but not clickable in the editor (they are in the read view); tags, chips and wikilinks follow on ⌘-click (see Notes links). Images stay as raw markdown. Editor colors are CSS variables in `src/app.css` for light and `.dark`, so a theme change needs no editor reconfigure. Each note keeps its own undo history while the page is open.

Fenced code is highlighted per language via `@codemirror/language-data` (each language is a lazy chunk, loaded on first use; unknown languages stay plain), with code colors scoped to code so they never restyle markdown. Typing `/` at a line start or after whitespace (not in words, URLs or code) opens a snippet menu (`@codemirror/autocomplete`): table, code block, task list, callout and today's date; the pure rules are in `src/lib/slash-menu.ts`. The `#` and `[[` link menus are two more sources in the same `autocompletion` config (`override`, so no word completion).

#### JSON notes

A note (and the scratchpad) has a `Kind`, `markdown` or `json`, stored on the row and switched from the editor header toggle or the note context menu ("Switch to JSON" / "Switch to Markdown"; `set_note_kind` and `set_scratchpad_kind`). Switching never rewrites the body, and new notes are markdown. JSON mode swaps the editor's extensions through a CodeMirror `Compartment` (`src/lib/editor/json-mode.ts`, applied to cached per-note states too): `@codemirror/lang-json` highlighting, folding, bracket matching and closing, and a lint gutter, with no live preview, `#`/`[[` completion or slash menu. The read view and Copy as HTML are markdown-only, so ⌘E does nothing on a JSON note.

Lint and Format/Minify share one parser, `@lezer/json` reached through `jsonLanguage.parser` (`src/lib/json-format.ts`). The printer walks the syntax tree and copies number, string and key text verbatim, so `12345678901234567890`, `1.0`, `1e5`, escapes and duplicate keys survive, which `JSON.parse`/`JSON.stringify` would not do. It indents by 2 spaces, keeps empty `{}`/`[]` compact and refuses any text whose tree has an error node ("Invalid JSON: line L, col C"). The lint diagnostic comes from the first error node of that same tree, not from `jsonParseLinter`, which mispositions errors under JavaScriptCore (the macOS WebView). Add no custom JSON parser.

In markdown editors (notes, scratchpad, handovers) a ```` ```json ```` block (info string `json`, case-insensitive; `jsonc` and `json5` do not count) shows Format and Minify chips on its opening fence while the cursor is inside it, and ⇧⌥F formats the block under the cursor (in a JSON note, the whole document). Blocks are found through the markdown syntax tree, so `~~~`, longer fences and list or blockquote nesting work, and the result keeps the block's indentation or `> ` prefix in one transaction (one ⌘Z). An invalid block shows the error beside the chips and changes nothing; blocks are not linted (`src/lib/editor/json-blocks.ts`).

JSON bodies are limited to 5 MB (UTF-8 bytes; `JSON notes are limited to 5 MB`), checked on body save and on switching to JSON; markdown has no limit and restore does not enforce it. A note over the limit (only possible after a restore) stays editable with an inline error and a "Switch to Markdown" action. JSON notes are kept out of body search, links and the semantic index; see Notes search and Semantic search.

The title is a separate field above the editor, not derived from a heading, because wikilinks need a stable, unique, user-controlled name. Rename commits on Enter or blur; Esc reverts.

Autosave is a pure queue in `src/lib/note-save-queue.ts` (tested in `tests/note-save-queue.test.mjs`): 800 ms after the last edit, plus a flush on note switch, window blur, the tab becoming hidden and leaving `/notes`. One save per note is in flight at a time and the latest text wins. Unchanged text is never sent. A failed save keeps the note in a page-level dirty set and is retried on every edit and flush; navigating away from `/notes` is blocked until it succeeds. ⌘N on the page creates a note; the palette's "New note" navigates to `/notes?new=1`, which runs the same create path (title focused).

#### Calculations (calc blocks)

A ```` ```calc ```` block in a markdown note (not JSON notes) holds formulas, and its results show live in the editor and the read view. The info string matches like `json`: first word, case-insensitive, `~~~` and quote or list nesting work, and an unterminated fence runs to the end of the note. Insert one with the slash item "Calculation".

Syntax: `name = expr` assigns, a bare `expr` shows its result, `//` and `#` lines and a trailing ` // text` are comments. Operators are `+ - * / ^`, parentheses, unary minus and `%` (`x + 10%`, `20% of x`). `sum` adds the lines above it back to the previous `sum`, a blank line or the block start (usable as `x = sum` or `sum * 2`). Variables are note-wide, top to bottom across all calc blocks, and using one before its definition is an error. `.` and `,` are both decimal separators and a space groups thousands (`1 380,50`, so `2 300` is 2300). A single trailing unknown word after a space, or a currency symbol, is a label and ignored (`1200 kr`, `€ 120`); a word glued to a number (`1e3`, `2x`) is an error; there is no unit or currency conversion. Results use a hand-made format (grouped with U+00A0, comma decimals, two decimals unless whole, not `Intl`, whose output differs between engines). A failing line shows a short red message and the other lines still evaluate; a `sum` skips failed lines and shows ` ⚠`. Clicking a result copies it as displayed, without the ⚠.

Results are display-only and never written into the body, so search, the semantic index, backup and sync see only the source. One pure evaluator, `src/lib/calc.ts` (a hand-written parser, no dependency; also finds the blocks in a markdown syntax tree), serves both views. The editor draws results as end-of-line widgets (`src/lib/editor/calc.ts`, `calcResultsPlugin`), and the `calc` `StreamLanguage` (`src/lib/editor/calc-language.ts`) highlights the source in the editor and the read view. Rust renders a calc block as an ordinary `<pre><code class="language-calc">`; `NoteReader.svelte` turns it into expression and result rows client-side through `src/lib/calc-reader.ts`, before code highlighting.

Because the transform is client-side, Copy as HTML (Notes page and scratchpad) exports a calc block as plain code, without results.

#### Read view and copy as HTML

⌘E (or the book/pencil button in the title bar) swaps the editor for a read view; the mode survives note switches and resets on page load, and creating a note always returns to edit. The editor stays mounted but hidden, so each note keeps its state. The read view renders the editor's current text, unsaved edits included, through the `render_markdown` command (`src-tauri/src/commands/markdown.rs`, `pulldown-cmark` with tables, strikethrough and task lists). It takes a `mode` (`read` or `copy`) and the database pool, because tags, chips and wikilinks are resolved against current data (see Notes links), so the same text can render differently after a rename.

The WebView has a strict CSP (`app.security.csp` in `src-tauri/tauri.conf.json`: no inline or remote scripts, no remote connections or images), but Rust also locks the HTML down itself: raw HTML is escaped and shown as text, only `http:`, `https:` and `mailto:` links are kept (others render as their text), and images never load (they become links labelled with their alt text). `src/lib/components/NoteReader.svelte` inserts the result, highlights code blocks with the editor's parsers and colors (`src/lib/editor/highlight-code.ts`), and opens links in the default browser through `tauri-plugin-opener`, checking the scheme again (`src/lib/links.ts`); a link never navigates the WebView. The capability grants only `opener:allow-open-url` with `opener:allow-default-urls` (http, https, mailto, tel).

"Copy as HTML" writes the same rendered HTML (`copy` mode: tags, wikilinks and chips become plain text) as `text/html` and the markdown source as `text/plain`, using a `ClipboardItem` whose HTML is a promise so WebKit's user-gesture requirement holds across the `invoke`.

#### Quit/close flush guard

An edit within the debounce window must survive ⌘Q. `src-tauri/src/flush_guard.rs` holds window close and app exit (`WindowEvent::CloseRequested` and `RunEvent::ExitRequested`), emits the `app://flush-request` event, and waits up to 2 s for the frontend to call the `flush_done` command, then closes or exits for real. A flag lets the re-entrant close/exit that Rust triggers itself pass through, so it does not loop. On the frontend, the root layout always listens for the event and runs the handlers pages registered with `registerFlushHandler` (`src/lib/flush-guard.ts`; `/notes` registers one that flushes all dirty notes), then calls `flush_done`. With no handler it replies immediately. No capability change was needed.

`AppHandle::restart` ignores `prevent_exit`, so the guard cannot hold a restart; code that restarts must call `flush_guard::flush_frontend` first (see Updater).

#### Updater

`commands/updater.rs` wraps `tauri-plugin-updater`; the frontend never calls the plugin. `check_for_update` returns `UpdateInfo` (version, current version, release notes) or `None`. `install_update` re-checks, downloads, verifies the minisign signature and installs (the plugin swaps the `.app` atomically and keeps the old one on failure), then flushes unsaved notes and calls `request_restart`; it returns only on failure, and a static flag allows one install at a time. Release builds check once on launch from the root layout (`src/lib/updater-state.svelte.ts`): an update shows a toast and a dot on the Settings gear, errors are silent. Settings › Preferences › Updates shows the version, a manual check with inline errors, and "Install and restart"; a pending update opens Settings on Preferences. Config, keys and CI are in `docs/configuration.md` (Updater and release signing).

On macOS the native app-menu Quit item sends `terminate:`, which tao turns into an unpreventable exit that skips `ExitRequested`. At startup `install_quit_menu` therefore replaces it with a custom "Quit" item (id `app-quit`, accelerator `CmdOrCtrl+Q`) that calls `AppHandle::exit`, which does go through the guard. It only applies when the default menu's app submenu ends in a Quit item; otherwise it logs a warning and keeps the native menu. The guard is unit-tested for its state machine only; it has not been verified in the real Tauri shell.

The frontend keeps TypeScript interfaces in `src/lib/types.ts` aligned with the Rust response shapes so route components can work with typed command results.

### Scratchpad

One persistent buffer for throwaway text, in a left slide-over drawer (`src/lib/components/ScratchpadDrawer.svelte`) mounted once in the root layout, so it works on every page. There is no backdrop: the page stays usable. ⌘J toggles it (fixed, not configurable), and so do the palette's "Scratchpad" action and the icon beside the Settings gear. It always starts closed on launch. It reuses the notes editor (`NoteEditor.svelte`) under a fixed pseudo-id, with tag and link following off, and its own save queue (`note-save-queue.ts`, 800 ms) plus a flush on blur and drawer close. It registers a flush handler, so quit flushes it too (see Quit/close flush guard). The read view (⌘E), Copy as HTML and the rendered links reuse `render_markdown` as for notes.

The pad lives in its own single-row `scratchpad` table, written by `commands/scratchpad.rs`. It is deliberately not a note: it stays out of notes search, `note_refs` (tags, wikilinks, backlinks), the semantic index and the palette's note hits, because none of those code paths see it.

The pad has a `Kind` like a note and the same JSON mode, 5 MB limit and Format/Minify (see Notes editor › JSON notes); Clear keeps the mode, and `set_scratchpad_kind` creates the row if the pad was never written. "Save as note" creates a note of the pad's kind, with the JSON rules above

Save as note asks for a title inline (Enter saves, Esc cancels the prompt only). `save_scratchpad_as_note(title, body)` takes the editor's live text, creates a root note with that body and clears the pad in one transaction, with the notes title rules (required, length, forbidden characters, case-insensitive duplicates; the error shows inline and the pad is untouched), then queues the note for embedding. Any pending pad save is cancelled first, so stale text never writes back over the cleared pad. Clear and a backup restore do the same: restore bumps `scratchpad.restored` in `src/lib/scratchpad-state.svelte.ts` and the drawer drops its state and reloads.

Key scoping: ⌘J is a capture-phase `window` listener in the layout (so it also works from inside editors), ignored while the palette is open or recording a shortcut, and when the palette's own saved shortcut is ⌘J (the palette wins). The drawer stops propagation of keydown events from inside it (bubble phase), so the notes page's ⌘N, ⌘F and ⌘E do not fire; ⌘K, a capture listener, still works. Esc closes the drawer only if nothing inside (slash or autocomplete menu, title prompt) already handled it, and focus returns to where it was. The Settings shortcut recorder rejects ⌘J ("⌘J opens the Scratchpad") through `recorderProblem` in `src/lib/palette.ts`; `validateShortcut` and `normalizeShortcut` do not, so a palette shortcut already saved as ⌘J keeps working. The drawer sits above page content and below modals, the palette and toasts.

### Playground

A page for writing, saving and running JavaScript, mainly to munge JSON notes. Scripts are saved documents in their own `scripts` table (`commands/scripts.rs`, `inner_*` plus thin wrapper), deliberately not notes: no `Kind` migration on `notes`, and code stays out of notes search, `note_refs` and the semantic index. Titles are trimmed, 1–200 characters, any characters, and not unique (a separate validator; notes' `clean_title` is not reused). `UpdatedAt` moves only on a real change.

**Why QuickJS, not an iframe.** Scripts run in `rquickjs` (QuickJS-ng), inside the Rust process, not in the WebView. User code gets no DOM, network or Tauri globals, so it cannot reach IPC or the database by construction. A sandboxed iframe was rejected: it would rely on Tauri's invoke-key check (wry's macOS handler does not filter by frame), needs the CSP loosened (`script-src 'self'` without `unsafe-eval`), and a busy loop there can't be reliably killed. The cost is about 1.2 MB of binary and no browser APIs.

**One run.** `run_script(code)` runs the editor's current text, unsaved edits included, and returns `{ run_id, outcome }`. `RunState` (managed state in `commands/playground.rs`) allows one run at a time app-wide (a second Run answers "A script is already running") and gives each run an id and its own cancel flag. `stop_script(run_id)` cancels only that run and is a no-op when idle or for a stale id; `script_running` returns the current id so a page that remounted mid-run can resync. The engine (`js_runner::run`, no Tauri types) builds a fresh `Runtime` and `Context` inside `spawn_blocking` per run, because the runtime is `!Send`; nothing JS-side survives a run.

**Limits** (`RunOptions::default`): 10 s wall clock, 256 MB heap, 1 MB stack. Captured output is capped at 1 MB or 10,000 lines; past that a "Output truncated" marker is added, further output is dropped and the script keeps running, but the final error and last value always show. An interrupt handler stops the run on timeout or Stop (it cannot be caught by `try`/`catch`). Errors are classified by flags the handler and engine set, not by message text, so `throw new Error("interrupted")` or `throw null` stays an ordinary user error; out of memory is detected from the engine's out-of-memory condition (the exception, or a null exception while usage is at the limit).

**Language.** Scripts are evaluated as sloppy-mode scripts (not modules) with top-level `await`. There are no timers, modules, `fetch` or DOM. After the main promise settles the job queue is drained under the same deadline, so floating async output is captured; a top-level promise that never settles with nothing left to run reports "Script is waiting on a promise that never settles". Rejections still unhandled when the run ends are reported, except the top-level one (that is the run's own error). Errors carry `line:col` parsed from the stack frame in `eval_script`.

**Output.** Returned in one batch when the run ends (no streaming): `console.log/info/warn/error/debug` lines with their level, plus the last expression value shown REPL-style (omitted when `undefined`). A small JS prelude (`js_runner/prelude.js`) formats values (pretty-printed objects and arrays, `[Circular]`, Map/Set, functions, strings quoted only when nested). It captures the intrinsics it needs before user code runs, reads properties defensively and falls back to a type tag if formatting fails, so a hostile prototype, getter or Proxy cannot crash the run. The frontend keeps output per script in memory (`src/lib/playground-state.svelte.ts`, which also holds the run status so a run survives leaving the page); it is never persisted, and a restore clears it.

**`note(title)`** is the only host function: synchronous and read-only. It matches the title case-insensitively (folded in Rust with `to_lowercase`, like the notes duplicate check) after trimming, and returns the parsed value for a JSON note or the body string for a markdown note; an unknown title throws `Note "X" not found`. It reads through the pool with `Handle::block_on` from the blocking thread. Scripts have no way to write notes.

**No panics on the run path.** Release is `panic = "abort"`, and the engine runs hostile code, so nothing between engine setup and the outcome may `unwrap`, `expect` or panic; host callbacks return `Result`, and note JSON is parsed with `serde_json` or in-engine `JSON.parse`, never rquickjs paths that `expect`. `rquickjs` is pinned to at least 0.14.0 because of an out-of-memory assert in older engine versions (CVE-2025-69654); an `#[ignore]`d release-mode stress test (`js_runner::tests::oom_stress_never_aborts`, run with `cargo test --release js_runner::tests::oom_stress -- --ignored`) checks that OOM never aborts the process. `rquickjs-sys` ships pre-generated bindings for `aarch64-apple-darwin` and `x86_64-apple-darwin`, so the build needs only a C compiler (no bindgen/libclang).

**Frontend.** `src/routes/playground/+page.svelte` has the list, an inline-editable title (Enter/blur commit, Esc reverts) and an inline delete confirm. Autosave reuses `NoteSaveQueue` (800 ms; its `isGone` matches "Script not found", so deleting a script stops retries) with a flush on script switch, navigation, blur, unmount and quit (`registerFlushHandler`). Run is ⌘↵ (bound at `Prec.highest`, since the default keymap binds Mod-Enter); Esc stops a run only when focus is in the editor or console and no popup is open. The editor host is `src/lib/editor/js-editor.ts`: highlighting through the lazy `@codemirror/language-data` JavaScript entry, a syntax-error lint from parse-tree error nodes, and completions (curated QuickJS globals, `console` members, note titles inside `note("`) added through `languageData`, not `autocompletion({ override })`, so the language's own local completions stay. No new npm dependencies; the pure helpers are in `src/lib/playground.ts` (tested in `tests/playground.test.mjs`). The palette's "New script" navigates to `/playground?new=1`, like `createNote`.

### Handovers

An end-of-day note to your future self, shown on Today the next working day. One markdown body per local date in its own `handovers` table (`commands/handovers.rs`, same `inner_*` plus thin wrapper pattern). Like the scratchpad it is deliberately not a note: no notes search, `note_refs` or semantic index, no title, no unique-title clashes. Dates are local `YYYY-MM-DD` strings computed by the frontend (`today()`); Rust only checks they are real dates. Saving an empty or whitespace-only body deletes the row; `DismissedAt` is never touched by a save, so a dismissed handover edited later (a checkbox in history) stays dismissed. "Save as note" (`save_handover_as_note`, the `*_and_queue` path so the note is indexed and queued for embedding) copies the stored body into a root note titled `Handover YYYY-MM-DD`; the handover stays, and a title collision comes back as the notes error shown inline.

There are two cards on Today, sharing one `HandoverCards` state object (`src/lib/handover-cards.svelte.ts`) that the page creates and passes to both: `HandoverIncoming.svelte` (the incoming/history card) and, directly under it, `HandoverToday.svelte` (today's editor), together at the bottom of the main column after the Tasks card. The history button lives on today's card and scrolls the history card into view. Neither card depends on the time entries and tasks loading: both mount at once and load on their own, but they stay hidden until the page's first load has settled (succeeded or failed), so they appear in place instead of jumping down when the sections above them render. A failed load still shows them. The pure rules are in `src/lib/handovers.ts` (tested in `tests/handovers.test.mjs`): `nextWorkingDay` (Mon–Fri, no holidays; Fri, Sat and Sun give Monday) and `selectIncoming`, which takes the single newest handover older than today and shows it only if it is not dismissed and today is on or after its next working day. There is no fallback to an older one (they stay reachable through ←/→ history, which includes dismissed ones). The incoming and history card is a read-only `NoteEditor`, but its task checkboxes tick and persist to that handover's body. The editor widget's checkbox is keyboard-focusable (Space/Enter, `src/lib/editor/task-keys.ts`) in every editor, so the read-only card is operable without a mouse.

Autosave reuses `NoteSaveQueue`, which keys by number: `handoverKey` maps a date to `YYYYMMDD` as an int, so the two cards share one queue and a save always lands on the date the text was written for. Today's editor captures its date when it opens and never reads `today()` at flush time. When the page sees the date change (it already reloads on focus or visibility), it flushes to the old date first, then switches. The queue flushes on blur, when focus leaves either card, when either card unmounts, on a day change and on quit (a `registerFlushHandler` handler, see Quit/close flush guard). On unmount the flush is kept in a module-level promise that a quick remount awaits, so it never loads stale text. The palette's "Write handover" action uses a request counter in `src/lib/handover-state.svelte.ts` (like `requestLogTime`): it navigates to `/` if needed and today's card scrolls into view and focuses its editor, whether it was already mounted or takes the pending request on mount. It waits for the page's first load to settle first (`pageSettled`), so sections rendering later can't push the caret off-screen.

⌘-click in either card follows a resolved `[[wikilink]]`: the queue is flushed, then the app navigates to `/notes?id=<id>`, the same deep link the palette and the scratchpad use. If that flush fails, the card shows the error and stays. Tags, `#task`/`#issue` chips and unresolved wikilinks can't be followed here, because the notes page follows those in place (a tag search, creating the note) and has no URL for them. The handover editors pass `followScope="notes"` to `NoteEditor` (a `linkFollowScope` facet in `src/lib/editor/links.ts`), which drops the ⌘-click hint, the pointer and the follow target from those links; the notes editor keeps the default `'all'`.

### Notes search

`search_notes` (in `commands/notes.rs`) queries the `notes_fts` FTS5 table (after splitting off `#tag` terms, see Notes links), which holds each note's title and a plain-text body from `markdown::to_plain_text` (markers and markdown link/image destinations dropped; raw HTML and autolinks are indexed as written). The `trigram` tokenizer matches case-insensitive substrings, which suits Swedish compounds; it can't match terms under 3 characters, so those filter the rows in Rust (Unicode case folding) without highlights. Every whitespace-separated term must match and is quoted, so FTS5 operators are plain text. Results are ranked with `bm25` (title weighted 10×), and hits come back wrapped in `\u0002`/`\u0003`, which are stripped from indexed text. The frontend splits them into `<mark>` segments (`splitHighlights` in `src/lib/notes.ts`) and never uses `{@html}`. The list re-searches only when the query changes, and rows are drawn from the current summaries, so the note you are editing never drops out mid-edit. The palette shows the top 5 hits under its commands once the query has 3 characters; shorter queries list commands only.

JSON notes are indexed by title only: `notes_fts` gets an empty body for them (`INDEXED_BODY` in `commands/notes.rs`, applied by every index write and rebuild), so they are findable by title but not by content, and their excerpt is empty everywhere (the tree, search list and ⌘K show the title and a "JSON" badge). `list_notes` selects an empty body for them through its own list-only query (`SELECT_NOTE_LIST`), so it never loads a JSON body; `get_note` returns the full body. Switching back to markdown re-indexes the body. The startup rebuild keyed by `NOTE_REFS_VERSION` covers `notes_fts` as well as `note_refs`, so a database that an older build indexed with JSON bodies is cleaned on the next start

`search_notes` takes an optional `hybrid` argument (default false, which is exactly the keyword search above). With it, and semantic search ready, semantic hits are fused in; see Semantic search.

### Semantic search

Opt-in hybrid search: an embedding model finds notes by meaning (Swedish and English, cross-language) and its hits are fused with the FTS5 keyword hits. Nothing downloads until the user clicks Enable in Settings › Preferences › Semantic search; until then, search is keyword-only and the notes search shows a hint linking to Settings.

**Model and runtime.** `ibm-granite/granite-embedding-311m-multilingual-r2` (Apache 2.0, ModernBERT, Swedish among its enhanced-support languages) as IBM's own int8 ONNX export (`onnx/model_quint8_avx2.onnx`, about 313 MB plus a 33 MB tokenizer, 768 dimensions; the model accepts 32k tokens, inputs are truncated to 512), run in-process on the CPU only (CoreML, which `ort` would otherwise register on macOS, is disabled so vectors are deterministic and match the calibration), by `ort` (ONNX Runtime, a prebuilt downloaded at build time; see `docs/configuration.md`) with the `tokenizers` crate. One fixed model, no picker; vectors store the model id, so a different model re-embeds everything. Granite takes no query or passage prompt and uses CLS pooling (the first token's vector, L2-normalised); `query_text` / `passage_text` in `embedder.rs` are where a model's prompts would go. It replaced `multilingual-e5-base` before release: on the calibration corpus it finds a relevant note for 95% of topic queries against 82.5% for e5 at similar precision, and matches fp32 more closely (top-10 overlap 0.90 against 0.83). `tract-onnx` (pure Rust) was tried first and dropped: about 3.1 s per 200-token chunk against about 0.35 s for `ort` on the dev host (2 vCPU x86_64), with e5. Granite takes about 0.6 s per chunk there (onnx-community's int8 export: 1.0 s), above the 200 ms-per-chunk target; on Apple Silicon e5 rebuilt the dev seed's notes in about one second and the app builds and runs with the prebuilt `ort` selects for aarch64-apple-darwin (checked by hand, 2026-11-07, with e5).

**Module layout** (`src-tauri/src/semantic/`): `model_files.rs` (pinned HuggingFace commit and SHA-256 per file; download, verify, remove), `embedder.rs` (`Embedder` trait, `OrtEmbedder`, a deterministic `FakeEmbedder` for tests), `chunker.rs` (heading-aware chunks), `index.rs` (`note_embeddings` rows, vector cache, worker), `fusion.rs` (ranking constants), `real_model_tests.rs` (opt-in, see `docs/development-notes.md`).

**Download.** Only GET requests, to huggingface.co (and its CDN redirects). Each file streams to `<file>.part`, is hashed, and is renamed only if the SHA-256 matches; HTTP, hash and disk errors delete the partial file and show an inline error with Retry. There is no resume. Cancel (and Remove) poll the cancel flag every 100 ms, so they return promptly on a stalled connection. Files live in `<data dir>/models/<model-id>/` (see Storage model); quitting mid-download leaves semantic search off and the stale `.part` is deleted at the next start.

**State and lifecycle.** `SemanticState` is managed Tauri state (an `Arc`). `semantic_search_enabled` (in `app_settings`) turns true only after download and verify succeed. One mutex (`lifecycle`) serialises enable, startup activation, Remove and Rebuild, so a download that finishes during a Remove cannot leave semantic search on without files. At startup: enabled and files present loads the model and catches up on missing or stale notes; enabled with files missing shows an error state with Download, never a crash. Status (`off`, `downloading`, `loading`, `indexing`, `ready`, `error`) is queryable with `get_semantic_status` and pushed as a payload-less `semantic-status` event (`semantic::STATUS_EVENT`); the frontend re-reads the status on each event (`src/lib/semantic-state.svelte.ts`) and on opening Settings.

**Worker and epoch.** Note writes (create, rename, body save, link rewrites, and customer/project renames, which re-queue all notes) enqueue the note id after their transaction commits through the `*_and_queue` helpers in `commands/notes.rs`; the queue dedupes by id. One background worker embeds queued notes one chunk per inference call, releasing the inference lock between chunks, so a query waits for at most about one chunk. Every input (chunk or query) runs alone: the int8 model quantises activations per run, so texts batched together would change each other's vectors. It skips notes whose content hash and model id are unchanged. Restore, Remove and Rebuild bump an in-memory epoch and clear the vector cache; the worker re-checks epoch and hash inside its write transaction and drops stale results, and a missing note (deleted meanwhile) is a skip, not an error. A failed inference is logged and the note skipped. Release builds use `panic = "abort"`, so tokenizer, inference and download paths must not panic: inputs are truncated to 512 tokens before inference.

**JSON notes are never embedded.** `process_note` checks `Kind` both when it reads the note and again inside its write transaction, so an embed already in flight cannot write rows for a note that just became JSON, and `enqueue_all` and restore skip them too. `set_note_kind` to JSON deletes the note's `note_embeddings` rows in its own transaction (evicting from the cache alone would leave rows that the next start reloads), and switching back to markdown queues it again. The "X of Y notes" progress counts markdown notes only

**Chunking.** Notes split on pulldown-cmark heading events into chunks of about 200 tokens with no overlap. Each chunk is embedded with the note title and heading path as a prefix, but `ChunkText` stores the body only; that is the snippet shown for semantic hits. Token counting is injected (the real tokenizer in the app, a word-count fake in tests).

**Hybrid search.** The vectors are an in-memory cache loaded from `note_embeddings`, searched by brute-force dot product (no `sqlite-vec`, no ANN). A note scores its best chunk. `search_notes` with `hybrid: true` runs the semantic leg only when ready and the query with `#tag` terms removed has at least 4 characters (tag-only queries stay keyword-only); `#tag` terms filter both legs. Both legs are cut to depth 50 and fused with Reciprocal Rank Fusion (k = 60). Granite scores sit in a narrow band that shifts with the query, so the similarity cut is relative (`similarity_floor` in `fusion.rs`): a semantic hit's best-chunk score must reach the median best-chunk score of all indexed notes for that query plus 0.05 (`MARGIN`), and never less than 0.76 (`ABSOLUTE_FLOOR`). The median is taken over every indexed note, before the tag filter and the depth cut. With fewer than 8 indexed notes the median says little, so a fixed 0.8375 (`FIXED_FLOOR`) applies instead. The values were calibrated at note level with the real model on a synthetic Swedish/English corpus plus off-topic queries: no rule tried separates relevant notes from noise cleanly, and this one favours not missing real matches (about 70% of off-topic queries still return a related note; a margin of 0.06 would cut that to 55% but drops relevant notes on the dev seed's sample notes, which sit 0.052–0.14 above the median). `real_model_sample_notes` checks it on those sample notes. Re-calibrate with `real_model_spike` if the model, chunking or prefix changes. Keyword hits past depth 50 are appended in keyword order, so a large `limit` never drops hits that plain search returns. Semantic-only hits come back with `related: true` (`NoteHit`) and their best-chunk snippet; the UI marks them "related".

The notes list and ⌘K search in two phases: keyword results immediately, then `hybrid: true` results after a 250 ms debounce, with stale responses dropped by the existing sequence guard. Pure helpers (merge, stale guard, status labels) are in `src/lib/semantic.ts`, tested in `tests/semantic.test.mjs`. The Search index Rebuild stays FTS-only; the Semantic search section has its own Rebuild.

### Notes links

`#tags` and `[[wikilinks]]` (`[[Title]]`, `[[Title|alias]]`; no heading links or embeds) follow Obsidian's rules, and Rust and the editor each implement them. `src-tauri/src/note_links.rs` walks pulldown-cmark events with byte offsets (skipping code, links, autolinks and raw HTML, and joining the text runs pulldown-cmark splits at `[`, `]` and table pipes) and returns tags and wikilinks with ranges. The one extractor feeds indexing (`note_refs`), `render_markdown` and rename rewriting. `src/lib/note-links.ts` is its TypeScript twin for the editor (scanning, `#`/`[[` triggers, slugs); both are tested against the shared case table `tests/fixtures/note-links-cases.json`, so change a rule in both places and add a case there.

Tags match case-insensitively and nest by prefix: `#acme` matches `#acme` and `#acme/website`. Customers and projects get tags from their names (lowercase, runs of characters not allowed in tags become `-`: customer `#<cslug>`, project `#<cslug>/<pslug>`); issues and tasks use their ids (`#issue/<id>`, `#task/<id>`, inserted by autocomplete and drawn as chips with the live title; an unknown id stays a plain tag). Entities are resolved at read time, so deleting one just leaves a plain tag, and deleting a note leaves its incoming links unresolved. To keep a slug owned by one entity, creating or renaming a customer (or a project within its customer) whose slug equals another's is refused ("Name clashes with tag #…"); a name whose slug is empty or all digits gets no tag, and so does a customer whose slug is `issue` or `task` (the chip namespaces; an existing customer named "Task" keeps its name but loses its tag, because renaming it would otherwise rewrite `#task/<id>` chips), along with its projects. `todo` is no longer reserved: `#todo/<id>` is a plain tag. Data that already collides gives the slug to the lowest id.

Renames rewrite bodies in the same transaction: a note rename retargets `[[Old]]`/`[[Old|alias]]` (case-insensitive) in other notes, and a customer or project rename rewrites its slug tags (nested ones too), only when it owned the old slug and the new slug is valid. Rewrites edit at the extractor's byte ranges, so code is untouched, re-index FTS and refs, and do not bump `UpdatedAt`. `rename_note` returns the ids of the notes it rewrote; the notes page then drops their cached editor state and queued saves and reloads the open note if affected (undo history of rewritten notes resets), so no stale body can restore the old title. Customer and project renames happen in Settings, where the notes page is unmounted.

`search_notes` treats each `#term` in the query as a tag filter (AND, prefix-nested) and the rest as the text search; a tag-only query lists every tagged note (the note list and ⌘K both). In the editor, resolution data (note titles, entity names, task status) sits in a CodeMirror `StateField` the page fills from `get_link_targets` and `list_tag_suggestions` (`src/lib/editor/links.ts`); ⌘-click follows (a wikilink opens its note, creating it first through `create_note_titled` when unresolved; a tag or chip filters the list). The read view follows on a plain click through `data-tag` / `data-note` attributes on the rendered anchors, checked before the external-URL path. A collapsible "Linked mentions" strip under the note lists the notes linking to it (`list_backlinks`, one-line snippet, no unlinked mentions).

### Frontmatter

A markdown note may start with Obsidian-style YAML frontmatter: a `---` line at the very top, closed by the next `---` or `...` line (trailing spaces allowed). Only the top counts; a later `---` pair stays a rule and a setext heading, which is why pulldown-cmark's metadata option (it matches anywhere) is not used. `src-tauri/src/frontmatter.rs` and its twin `src/lib/frontmatter.ts` find the block and read two keys with a small YAML subset (`key: a, b`, `key: [a, "b"]`, or `- a` lines below `key:`; keys case-insensitive; anything else ignored); both pass `tests/fixtures/frontmatter-cases.json`.

- `tags:` values are tags (a leading `#` optional): indexed in `note_refs`, rewritten by customer and project renames, and highlighted in the editor. A value that is not one whole valid tag is ignored. Other frontmatter text is never scanned for `#tags` or `[[links]]`.
- `aliases:` values resolve wikilinks to the note (`get_link_targets` returns them as `aliases`; the read view's resolver and `list_backlinks` use them too). A note title wins over another note's alias. `[[` completion offers titles only, and renaming a note does not rewrite links to its aliases.
- The editor shows the block as muted monospace source (Lezer still parses it as markdown, so live preview and `blocks.ts` skip nodes inside it); the read view shows it as written in a muted block, and Copy as HTML drops it. The list excerpt and semantic embeddings skip it; full-text search still indexes its text.

### Notes folders

Rules and data semantics (name validation, suffixing on clashes, delete-to-parent, manual order, restore) are in `docs/data-and-backup.md`. Rust owns them in `src-tauri/src/commands/folders.rs`; the frontend only builds the view.

Pure tree logic lives in `src/lib/folders.ts` (tested in `tests/folders.test.mjs`): building the tree from the flat `list_folders` and note summaries (server order is kept; the client never sorts by name or date), flattening to the visible rows, folder paths, descendant sets, valid move targets, the keyboard action table and drag-and-drop helpers. `src/lib/components/NoteTree.svelte` renders one flat keyed `{#each}` over the visible rows (keys `f:<id>`/`n:<id>`, indentation per row, so `animate:flip` works across levels), with ARIA `tree` roles and keyboard navigation (↑/↓, →/←, Enter/Space, F2 to rename). Drag and drop uses pointer events with a 5 px threshold, not HTML5 DnD; drop targets are found with `elementFromPoint` and `[data-drop-folder]`. A collapsed folder under the pointer auto-expands after 600 ms (reverted if the drag is cancelled), the list auto-scrolls near its edges, Esc cancels, and dragging is off while searching. Order is manual (see `docs/data-and-backup.md`, Manual order): dragging between rows shows a sky insertion line and calls `move_note`/`move_folder` with an `index`; dropping on a folder row's middle moves into it (top of a note's group, end of a folder's), its top/bottom quarter means before/after. A note can only target note slots and a folder only folder slots (a note's slots stay within its pin group). ⌥↑/⌥↓ moves the focused row one step among its siblings and keeps focus. The page reorders optimistically, invokes, then reloads; on error it shows an inline message and reloads. `upsertNote` in `src/lib/notes.ts` replaces a row in place (an edit never re-sorts) and uses a comparator `(pinned DESC, position, id)` matching the server. Search results keep relevance order. `src/lib/components/MoveToDialog.svelte` is the keyboard alternative: a folder picker (every valid destination by full path, excluding the item's own subtree) opened from the editor header or from a row's context menu. The tree's context menu (`src/lib/components/ContextMenu.svelte`, one instance rendered by `NoteTree`, positioned by the pure `placeMenu` in `src/lib/context-menu.ts`) opens on right-click, Ctrl+click, or Shift+F10 / the ContextMenu key (anchored under the focused row), with folder, note and root ("Notes") item sets; the native WebView menu is suppressed on tree rows only. The hover buttons stay. Note delete from the menu uses an inline confirm on the row, like folders. The notes page owns the current folder (the last clicked folder or the open note's folder): ⌘N, `+` and `create_note_titled` create there, and the list reloads from the backend after every move or delete.

The expanded set is persisted through `get_expanded_folders`/`set_expanded_folders` (debounced; ancestors of the open note always expand).

### Tasks

One list replaced the old Todos kanban and Reminders page. A task is open or done, has an optional due date (and time), an optional repeat, optional links to one issue and one note, and 0 to 10 reminders. Rust owns all state and recurrence math (`src-tauri/src/commands/tasks.rs`, `src-tauri/src/recurrence.rs`); the frontend only parses typed input for live previews (`src/lib/time-phrases.ts`, English and Swedish) and groups, orders and labels what Rust returns (`src/lib/tasks.ts`, tested in `tests/tasks.test.mjs` and `tests/time-phrases.test.mjs`). Tables and backup details are in `docs/data-and-backup.md`.

**Due and order.** A due time needs a due date (setting a time with no date sets today). Due never notifies by itself. Open tasks sort by due date, due time (untimed last), then created; there is no manual order and no status beyond open/done. Overdue means a date before today, or today with a time that has come.

**Reminders.** Each is relative to the due (`OffsetMinutes` before it: at due time, 15 min, 1 h, 1 day, 1 week) or a custom absolute time (`At`, must be in the future when saved). A relative reminder on a date-only due counts from 09:00 on that day; on a task without a due date it stays stored, never fires and shows "Needs a due date". The fire time is derived, never stored, except as `FiredFor` (the time the reminder's `State` applies to). Times are naive local wall-clock strings (`%Y-%m-%dT%H:%M:%S%.3f`), so "09:00" stays 09:00 across DST and time-zone changes; a time inside a DST gap fires at the first valid minute after.

**Reminder states.** `pending` -> `sent` (notified) -> `dismissed` (the toast x, or silently). Only `sent` counts as overdue. Toast actions: Done completes the task, Snooze sets `SnoozedUntil` and puts that one reminder back to pending (the due is never changed), x dismisses. `reconcile_reminders` runs in the same transaction as every write that can move a fire time (due, offset, custom time, sync's due writes): a reminder whose time moved to the future re-arms to `pending` (snooze dropped); one whose new time is already past becomes `dismissed` without a notification, so editing a due date never spams. Completing a task leaves its reminder rows alone but they stop firing; reopening silently dismisses those whose time has passed. Phone import follows the same rule.

**Repeat.** none, daily, weekdays (Mon-Fri), weekly on chosen weekdays, or monthly on a day 1-31 (a shorter month uses its last day); it lives on the task and needs a due date. Only completion advances a repeating task, Apple-style: an uncompleted occurrence stays on its date and shows overdue (there is no auto-advance, unlike the old recurring reminders). Completing moves the due to the first occurrence strictly after the later of the due and now, at the due's time (09:00 for a date-only due), and the task stays open; missed occurrences collapse into one. Relative reminders re-arm for the new occurrence. Custom reminders fire once: on advance a `sent` custom reminder becomes `dismissed`, a `pending` one stays. Repeating tasks are Mac-only (never synced).

**Completion and Undo.** `complete_task` returns the task and a `TaskUndo`: the exact pre-completion snapshot (done flag, due, every reminder's state, snooze and `FiredFor`), which the frontend hands back to `undo_complete_task` within about 5 s (`UNDO_WINDOW_SECS`, `UNDO_MS`). Undo applies only while the task is still exactly as the completion left it (`UpdatedAt`, done flag and due all match); otherwise it fails with "The task changed meanwhile, so it can't be undone", and a second undo of the same snapshot fails the same way. The Apple Reminders sync nudge for a completion waits 6 s and sync skips a completion younger than the window, so an undone completion never reaches the phone.

**Links.** Deleting an issue or a note unlinks its tasks (`ON DELETE SET NULL`), never deletes them. "Create issue from task" is kept (`create_issue_for_task`). Deleting a task deletes its reminders (cascade) and its phone item on the next sync pass.

**Scheduler.** `task_scheduler::run` is spawned in `setup` (like the semantic worker) and ticks every 30 s, the first tick immediately, so reminders that came due while the app was closed fire as a catch-up. Each tick calls `inner_fire_due`: for every pending reminder of an open task it computes the fire time in Rust (row counts are tiny) and writes `pending -> sent` with a conditional `UPDATE` that also matches the reminder's `FiredFor`, `SnoozedUntil` and the task's `UpdatedAt`, so a concurrent edit, snooze or completion wins and a stale time never fires; a reminder whose `FiredFor` no longer matches is reconciled silently instead. Only the reminders it sent are notified: one task gets its own notification ("Reminder", the task title, and "Note: <title>" when linked); two or more tasks (launch catch-up, sleep/wake, restore) are batched into one ("3 reminders: A, B, ..."). Delivery is at-most-once and there is no re-nag: a failed send still counts as sent. The native notification is skipped while the main window is focused, because the toast covers it, and for a reminder the phone already alarms for (see Apple Reminders sync). Skipped reminders still fire, toast and count on the badge. Errors are logged and the loop continues (no `?` exit, no `unwrap`; release is `panic = "abort"`). The tick is unit-tested through the `TaskSink` trait (`tick` against a fake sink); the real notification, click, focus check and badge are not tested. The dock badge is the overdue count (open tasks past due, or with a sent reminder); because it changes with the clock, every tick recomputes it, not only fires.

**Events.** Rust emits:

- `tasks-changed` and `reminders-changed` (no payload, always together): the scheduler on every send, and every command wrapper that changes tasks or reminders, directly or by cascade or hook, through `task_scheduler::tasks_changed(&app, pool)`: the task commands, `rename_note`, `delete_note`, and restore. That helper also recomputes the dock badge and nudges Apple Reminders sync; sync's own writes use `tasks_refreshed`, which skips the nudge, and completion uses `tasks_changed_later` (delayed nudge, see Completion and Undo). A new write path that can change, cascade-delete or complete tasks must call one of them, or the UI and badge go stale until the next tick.
- `tasks-open` (payload `{ task_id: number | null }`): a notification click. Rust shows, unminimizes and focuses the window; the root layout then navigates to `/tasks?id=<id>` (`null` for a batch opens `/tasks`). Today rows and toasts open tasks the same way.

**Frontend.** `src/lib/tasks-state.svelte.ts` holds the shared list, re-read on both change events (bursts coalesce) and on window focus; `/tasks`, the Today card, the nav count, the reminder toasts and the Undo toast all read it. The nav tab and Today recompute the overdue count from a 30 s clock as well as on events. `/tasks` has quick-add with a live parse preview (`planQuickAdd`: a parsed date becomes the due date, a typed time becomes the due time plus an "At due time" reminder, a time with no date means today, nothing parsed means no due, and the first `#tag` links an issue), a details side panel (`TaskPanel.svelte`, which replaced TodoModal) where reminders are added from presets or a custom time, and a completion animation (pop, tick, sparks, strike, slide-out, instant under reduced motion) shared by every row (`TaskRow.svelte`). Groups are by `due_date` only: Tomorrow, then This week (after tomorrow through Sunday of the Monday-start week, so it can be empty on a weekend), then Later. The scope filter (`TaskScope`, `scopeTasks`/`scopeCounts` in `src/lib/tasks.ts`) is cumulative: Today is overdue plus today, Tomorrow is tomorrow only, This week is overdue through Sunday, All is every open task including undated; its state is `taskView` in `tasks-state.svelte.ts` (module state, not persisted). Revealing a task outside the scope (⌘K, a notification, `?id=`, quick-add) switches back to All. Rows on `/tasks` and the Today card show hover/focus row actions: Schedule (`schedulePresets`/`scheduleInput`, which change only the date, keep a due time and go through `update_task`, so the backend reconciles reminders; "No date" clears date and time), Details (`/tasks` only) and a More `ContextMenu` (Complete, Delete with an inline confirm and no undo, Copy link as `#task/<id>`). The reminder toast stack (`ReminderToasts.svelte`, mounted in the root layout; the older `Toast.svelte` stays for plain messages) is derived from `sent` reminders on open tasks, not from transient events, so catch-up and reloads are not lost: up to 3 toasts with Done, a Snooze menu and an x (dismiss), then "+N more" linking to `/tasks`. Creation paths: quick-add, ⌘K "New task" (same mapping, also `remind ...` / `påminn ...` with a live preview), "Remind me..." in the note row context menu (a task linked to the note with a custom reminder), and the Today card's +.

**Notifications plugin.** `tauri-plugin-notification` is a Rust-only dependency: there is no `@tauri-apps/plugin-notification` package, notifications are sent and clicks handled in Rust, and the dock badge is set from Rust (`WebviewWindow::set_badge_count`). The only capability entry is the read-only `notification:allow-is-permission-granted`, which silences a rejection from the plugin's JS shim; JS still cannot send notifications.

**Caveats.**

- Task reminders fire only while the app runs. Closing the window quits (see Quit/close flush guard); the launch catch-up covers what was missed. There is no menu bar or close-to-hide mode.
- Notification permission cannot be detected or requested on desktop: the plugin's `request_permission` always reports granted, so a user who denied notifications in macOS System Settings gets no error, only silence (the toast and badge still work). Release builds are signed with a self-signed certificate (see `docs/configuration.md`, macOS code signing), so the permission should survive updates; local ad-hoc builds may lose it on each rebuild, and dev builds are attributed to Terminal. The same applies to the Reminders access grant that sync needs.
- The scheduler's click handler must be installed before the first notification is shown, or the plugin does not report clicks on it (`install_click_handler`, called in `setup` before the spawn).
- Native notifications, notification click, focus suppression and the dock badge have not been verified in the real macOS app: only the logic around them is unit-tested, and the UI was checked as mocked renders.

### Apple Reminders sync

Opt-in two-way sync of open tasks with one Apple Reminders list through EventKit, so iCloud carries them to the iPhone (native alerts there, create/edit/complete/delete there, changes flow back). No server and no iOS app. Off by default; the switch, access state, last sync, last error and skipped items are in Settings › Preferences. Table and backup details are in `docs/data-and-backup.md`.

**Layout.** The engine (`src-tauri/src/apple_sync/engine.rs`, `run_pass`) sees only the async `ReminderStore` trait and the pool, so all merge logic is unit-tested on any OS against an in-memory fake (`fake.rs`, `cfg(test)`, which models several alarms per item). The EventKit store (`eventkit.rs`) is `cfg(target_os = "macos")`; elsewhere `UnsupportedStore` reports sync as unavailable and the objc2 crates are not linked. `EKEventStore` is `!Send`, so one dedicated OS thread owns it and runs jobs sent over a channel; the async methods wait on a oneshot and never block the main thread (a call times out after 30 s, because the pass holds the sync lock). Release is `panic = "abort"`: nothing in EventKit code unwraps. `badger_writes.rs` holds the conditional, column-limited Badger writes (reusing the validation in `commands/tasks.rs`), and `runner.rs` the background task.

**List.** One list, "Badger" ("Badger Dev" in debug builds). It is created in the source of the default list for new reminders and afterwards identified by the stored `calendarIdentifier` (`app_settings`), not by name, so renaming it on the phone is fine. Turning sync off keeps the list and pairings; turning it on again resumes (missed-pass counts start over).

**Scope.** Open tasks, one-off and not Mac-only. Repeating tasks stay Mac-only: a task that becomes repeating is deleted from the phone and unpaired; one that stops repeating is pushed. A task that is done when sync is first enabled is not pushed. A phone item with a repeat rule is imported as a one-off and the rule is stripped on the phone. Synced fields: title, notes, due and completed. A phone item's due is a date or a date-time: a date-only phone item imports as a date-only task (no 09:00), and a task's date-only due stays date-only on the phone. Issue and note links, reminder states and `MacOnly` stay Badger-only. A task created on the phone lands as an open task with title, notes, due and alarms; an item with no title is skipped (counted in Settings as "needs a title", retried every pass).

**Alarms.** Badger owns reminders, so each pass sets the phone item's absolute `EKAlarm`s to exactly one per Badger reminder, computed from the due (relative offsets) or the custom time and recomputed when the due changes, including when it is changed on the phone. Phone alarm edits are overwritten; relative alarms the phone set are left alone. Alarms already in the past stay on the item once pushed (so they aren't churned or cancelled as they pass) but are never newly pushed. `apple_sync_items.PhoneAlarms` records what was pushed. On import, the phone's absolute alarms become reminders: one equal to the due time is "At due time", the others are custom, alarms already past are stored `dismissed`, and beyond 10 the earliest 10 are kept (the rest are overwritten on the next push). Snoozes are Badger-only and never pushed.

**Keep off phone.** Any task can be kept Mac-only with the `MacOnly` column (default 0, synced). Mac-only rows are out of scope like repeating ones: never pushed; a paired row that becomes Mac-only has its phone item deleted and its pairing dropped (not a Badger delete); turning it off pushes it again on the next pass. A Mac-only task is never deleted in Badger because its phone item vanished (it only unpairs, also under "Delete in Badger anyway"), and it counts toward neither mass-delete guard. Phone-created items are never Mac-only. The flag is set from the details panel's "Keep off phone" switch (create/update inputs carry an optional `mac_only`; omitted, create syncs and update keeps the flag). The switch and a "Mac only" laptop mark show only while sync is on (shared `appleSync.on`, `src/lib/apple-sync-state.svelte.ts`).

**Pairing and merge.** `apple_sync_items` pairs one task with one EventKit item and stores each side's synced fields as of the last sync (`BadgerSnap`, `PhoneSnap`). A pass merges per field, three-way against those snapshots: one side changed, take it; both changed the same field, Badger wins. Completion is its own field, so a phone completion survives a Badger title edit; a phone completion also stops the task's reminders ("done wins" over a snooze). EventKit ids are device-local, so the external id is stored too, and a pairing whose id vanished is re-matched by it.

**Pass flow.** `run_pass` never fails: errors land in the report and in `app_settings` (last sync, last error, paused reason, skipped list). Order: check access, resolve or create the list and fetch it (completed items included), run the mass-delete guard, process pairings, then push unpaired Badger tasks and import unpaired phone items. A completion made in Badger less than `UNDO_WINDOW_SECS` ago is left for a later pass (see Tasks, Completion and Undo). Per-item failures are collected and the pass continues; a pass is idempotent, so a partial failure is retried. Badger's own writes go through conditional UPDATEs that name the columns they change, so a pass cannot clobber a concurrent edit.

**Triggers.** `runner::run` is spawned in `setup` and runs a pass at launch, on a nudge after a 1.5 s debounce, and every 60 s (iCloud changes don't always announce themselves). Nudges come from Badger write paths (`tasks_changed`, restore, dev seed), from EventKit's store-changed notification, and from enabling sync or granting access. For 5 s after a pass that wrote to Reminders the store-changed notification is ignored as its own echo. `SyncHandle.lock` serializes passes with each other and with restore, and Settings' "Sync now" runs a pass under it. iCloud latency is seconds to about ten minutes, so phone edits are not instant.

**Deletes and guards.**

- Badger deletes a task: the phone item is deleted. A phone delete of a completed item (e.g. iOS "Clear completed") only drops the pairing; Badger keeps its done task.
- A phone delete of an open item deletes the task in Badger (its reminders cascade), but only once the item has been missing for two consecutive passes (`MissedPasses`), so a one-pass iCloud glitch deletes nothing. If Badger edited the task since the last sync, Badger wins and the item is pushed back.
- Mass-delete guard: no access, a missing list, or a fetch that returns zero items while two or more open pairings exist (a lone item cleared on the phone falls to the two-pass rule instead) pauses sync and deletes nothing; so does more than half (and at least 3) of the open pairings going missing in one pass. Settings shows the error: "Grant access" (access), "Recreate list" (list missing; recreating drops the pairings so Badger pushes its tasks again), or "Delete in Badger anyway" (empty fetch only, behind an inline confirm). Delete anyway applies phone deletes at once, and only if the stored pause is still `empty_fetch`; a stale click runs an ordinary pass.

**Restore.** Pairings are not in backups, so restore keeps them and sets `apple_sync_restore_pending` inside its transaction (a crash can't lose it). The next pass is Badger-authoritative: Badger wins every field, phone items whose Badger row is gone are re-created from Badger, and nothing is deleted in Badger. A pairing whose task is not in the restored data is dropped and its phone item is imported again as a new task. The flag clears after a pass with no errors.

**Notifications.** The phone alarms; Badger skips its native macOS notification (`apple_sync::phone_alarms_cover`, called from the scheduler tick) for a reminder only when sync is enabled with no pause or error, its task is paired, one-off and not Mac-only, and the reminder's fire time is among the pairing's `PhoneAlarms`. Otherwise (not yet pushed, paused, access lost, repeating, Mac-only, snoozed to a time the phone doesn't have, time changed on the Mac but not yet pushed) it notifies as before. Toasts and the dock badge are unchanged.

**Events.** `apple-sync-status` (Settings re-reads status). A pass that changed tasks emits the same `tasks-changed` / `reminders-changed` pair as any task write, through `tasks_refreshed` so it does not nudge itself.

**Access and permissions.** Settings' Grant access button requests access (full access on newer macOS, the older entity-type request otherwise) and, once denied (macOS asks only once), opens the Reminders pane of System Settings. `src-tauri/Info.plist` carries the usage strings (`NSRemindersFullAccessUsageDescription`, `NSRemindersUsageDescription`) and Tauri merges it into the bundle; the app is not sandboxed, so no entitlement is needed. Release builds are signed with a self-signed certificate (see `docs/configuration.md`, macOS code signing), so the grant should survive updates; local ad-hoc builds may be asked again after each rebuild.

**Known limits.**

- A phone item that is completed and then cleared before a pass sees it completed looks like an open item that was deleted, so after the two-pass rule Badger deletes the task instead of marking it done. Cleared after a pass saw it completed, it only unpairs.
- Restore can re-import synced items that are absent from the backup (they come back from the phone as new tasks).
- Issue and note links, repeating tasks, Mac-only tasks and reminder states stay Badger-only.
- Several API-set alarms on one item: whether the iPhone shows all of them is unverified (they should still fire). The trade-off was accepted; check on a real device before relying on more than one reminder per phone item.
- Not verified on a real device by the author of the change: EventKit access, list creation, iCloud round trip, multi-alarm push and import, and notification suppression. Test with a bundled debug build; an unbundled `tauri dev` binary may lack the usage string and be killed by TCC.

## Storage model

Badger keeps runtime files in different locations by build type:

Development (`npm run dev` / debug builds):

```text
.badger-dev/badger.db
.badger-dev/logs/
.badger-dev/backups/
.badger-dev/models/
```

Non-debug builds:

```text
~/.badger/badger.db
~/.badger/logs/
~/.badger/backups/
~/.badger/models/
```

The schema is created on startup if it does not exist. The main tables are:

- `customers`
- `projects`
- `issues`
- `time_entries`
- `tasks` (see Tasks)
- `task_reminders` (see Tasks)
- `travel`
- `notes`
- `folders` (note folders, see Notes folders)
- `scratchpad` (single row, see Scratchpad)
- `handovers` (one row per local date, see Handovers)
- `scripts` (playground scripts, see Playground)
- `apple_sync_items` (Apple Reminders pairings, see Apple Reminders sync; device-local, not in backups)
- `note_refs` (derived link index, see Notes links; not in backups)
- `note_embeddings` (derived semantic index, see Semantic search; not in backups)

Foreign keys are enabled, and cascading deletes are used to keep related records consistent.

## Runtime behavior with weight

### SPA mode is required

The root layout disables SSR because Tauri APIs only exist inside the WebView at runtime. Frontend code is therefore written as a client-only application.

### Rust owns persistence and file access

The frontend does not talk to SQLite directly and does not read or write backup files on its own (restore reads and gunzips through `read_backup_file`). File-system work stays in Rust commands, which keeps native access behind a single boundary.

### Development-only seed data is gated by debug builds

`dev_seed` is compiled only with `debug_assertions`, and the seed command is registered only in debug builds. Production bundles therefore do not ship the seed workflow.

### Logging is file-based

The backend initializes daily-rotating logs under repo-local `.badger-dev/logs/` in debug builds and `~/.badger/logs/` in non-debug builds. It keeps the logging guard alive in managed Tauri state so writes do not stop early.

### Automatic startup backups

On each application startup, Badger creates a backup if the retention setting is greater than zero. The backup is written, gzipped, to `backups/YYYY-MM-DD/backup.json.gz` beside the active database, overwriting any existing backup for today (atomic write; a leftover legacy `backup.json` from the same day is removed). Listing and trimming accept either name and prefer the `.gz`. After backup creation, old backups are automatically trimmed to keep only the most recent backups based on the retention setting (default: 3). Setting retention to 0 disables automatic startup backups entirely. Backup creation, trimming, and listing logic stays in Rust; the frontend only displays the available backups and retention setting.
